Meter, front page

Home, redesigned

A plan that fits what P2 actually finished, and a mock at full fidelity so the colour, type and density can be settled before any code is written. Four decisions are marked. One of them is a real defect in the palette that is shipping today.

Built on Datadog DRUIDS, Bach dashboard patterns, AWS Cloud Intelligence IA P2: 20 of 25 done Palette from tokens.css Figures below are example data
1

Why it reads as vague

Three separate causes. Only the third is a design problem, and it is the one worth fixing first because it is the one that is free.

cause 01

Most panels have no data yet

Five of six slots read not yet collected and name P1, P3 or P5. That is correct behaviour, not a bug. It is also most of the screen.

cause 02

Two panels are showing a parse error

Only in the dev server, which serves index.html for /api. On the compose stack those two render. Not a product defect.

cause 03

Nothing outranks anything else

Six identical bordered blocks, one type size, no severity, no coverage, no shape. An absence is drawn at the same weight as the money. This is the real one.

4

Decision one: severity collides with interactive

In tokens.css today, --severity-5 and --accent are the same colour, #1f4f8f. So the most severe finding is painted the exact blue that everywhere else in the product means "this is a link". That breaks the documented rule that colour is interactive-only, and it is the strongest reason the screen reads as undifferentiated.

A. Keep itno change
12345 = accent

Sequential and ordered, as documented. But critical and clickable are indistinguishable, and the ramp's light end is nearly the page background.

B. Warm ramprecommended
12345

Still one sequential hue, still ordered, and now severity can never be confused with a link or with a failure. Blue stays interactive, red stays failure, amber stays freshness. Each colour keeps one job.

C. Neutral rampmost austere
12345

Severity by weight alone. Maximum honesty, zero colour collision, and it survives any print or colourblind case. Reads as flat when a page is mostly low severity.

Either way

The shape stays redundant with the colour. A severity chip is a square plus a word, never a square alone, so the ramp is never the only carrier of the meaning. That is already the rule in docs/12-UI-DESIGN.md and the mock keeps it.

Decision two: the typeface is not what the doc says

docs/12-UI-DESIGN.md specifies JetBrains Mono or IBM Plex Mono for numerals and Inter or IBM Plex Sans for prose. tokens.css ships system-ui and ui-mono​space. One of the two is wrong and should be corrected.

Zero bytes, zero network, no font swap. But it is a different face on every machine, so density and column widths are not the same for two people looking at the same screen.

B. IBM Plexrecommended

What the design doc already asked for, and what this page is set in. Genuinely tabular, identical everywhere, and self hosted so there is no third party request from a page showing customer spend.

6

Decision three: how an absence is drawn

The rule stays: an unfilled slot names the sub project that will fill it, and never renders as zero or blank. The question is only how much of the page that claim is allowed to occupy.

A. Full cardstoday

Five bordered blocks at the same weight as the money. Roughly 60 percent of the screen is a promise about the future. Honest, and it is what makes the page look empty.

B. One railrecommended

One 44 px strip below the fold carrying all five names, as in the mock. Same information, one twelfth of the space, and it still turns into a tile when each sub project lands.

C. Hide entirelyrejected

Cleanest looking, and it breaks the progress view. A reader can no longer tell the difference between "not built" and "nothing found", which is the exact confusion the product exists to prevent.

7

Decision four: density of the summary strip

The design doc sets 32 px rows for tables and "generous" for a single judgement. It does not say what a summary tile is. The mock uses four tiles at 104 px. Three would be calmer, five would need a second row at 1440 px. Four is the recommendation, and it is the only one of the four decisions that is purely taste.

8

What does not change

Home owns no data

Every figure is still read through the detail screen's own hook and query key, so the two can never disagree. The tiles are roll ups, not new queries.

A failure is never a number

The UNKNOWN row in the mock shows the typed cause and the words "not a number" where a figure would sit. It is never a zero and never a blank.

Two timestamps, always

as of 04:00 today is absolute, collected 6 min ago is an age. Never "live", because Meter is never live.

Coverage is persistent

The trust strip sits above the money and stays there. It is not a toast, and it names the source, which is the Bach meta information pattern applied literally.

Before anyone signs off on the look

None of this has run against a real AWS account. The mock's coverage reads 3 of 3 accounts because the seeded local estate has three. Against a real organization the first honest render of this page is far more likely to be a partial coverage line and several typed failures, which is the state worth designing for and the one hardest to make look good.

That is an argument for deciding the failure and partial states now, with the palette, rather than after the happy path is built.
