These rules are binding for every contributor, human or agent. They sit on
top of the global rules and override them where they conflict.

## Writing rules

1. **No em dashes anywhere.** Not in code, comments, documentation, commit
   messages, UI copy, or generated output. Use a comma, a colon, parentheses,
   or restructure the sentence. En dashes are also banned. The only acceptable
   dash is a hyphen inside a compound word or a list bullet.
2. Plain English. No filler, no marketing voice, no hedging.
3. Every number in a document states whether it is measured or modelled.
4. Absolute dates only. Write `2026-08-23`, never `tomorrow` or `last week`.

Enforced by `make check-writing`, which runs inside `make verify` and in the
pipeline. It scans markdown, Python, TypeScript, Terraform and YAML.

```bash
make check-writing
```

The literal characters are deliberately not reproduced in this file. Writing
them here would make the check fail on its own documentation, which is exactly
what happened the first time this rule was written down.

## Documentation maintenance

Documentation is not optional output produced at the end. It is updated as
part of the same change that makes it stale.

**Routing rule: `docs/03-CHANGE-CONTROL.md` states where each kind of change
is recorded. Read it before writing anything down.**

| Document | Update trigger | Owner |
| --- | --- | --- |
| `INDEX.md` | Every material change. It is the only document a newcomer is guaranteed to read | Author of the change |
| `docs/features/FEAT-nnn-*.md` | Any change to what a feature does. Every feature has exactly one | Author of the change |
| `docs/architecture/file-graph.md` | Generated. Run `make graph`, never hand edit | Generated |
| `security/POSTURE.md` | Generated by `make security-scan`, never hand edit | Generated |
| `tasks/STATUS.md` | End of every work session | Whoever did the work |
| `tasks/ISSUES.md` | The moment an issue or open question is found or closed | Finder |
| `docs/checkpoint.md` | End of every completed task | Whoever did the work |
| `project_map.md` | Any new module, moved module, or changed responsibility | Author of the change |
| `context_index.md` | Any new or removed public function or class | Author of the change |
| `docs/01-ROADMAP.md` | Sub project status change | Whoever changed the status |
| `docs/adr/` | Any decision that is expensive to reverse | Decision maker |
| `tasks/lessons.md` | Every time a correction is received | Recipient of the correction |

Batch these updates into one commit at the end of a task. Do not write one
commit per document.

## Definition of done

A change is done when all of the following are true.

- Tests exist and pass, and coverage for the changed area is at or above 80 percent.
- Errors are typed and surfaced, never swallowed and never collapsed into zero.
- No secrets, no hardcoded account identifiers, no hardcoded region strings.
- `tasks/STATUS.md` and `docs/checkpoint.md` reflect the change.
- Commit message follows the format below.
- `INDEX.md` reflects the change, and `make check-docs` passes.
- The feature document under `docs/features/` reflects the change.
- `make security-scan` passes with zero findings.
- Any new dependency was admitted through `make dep-check`.
- A staff engineer would approve it in review.

Reading your own code back is not evidence. Running the test and pasting the
output is evidence.

`make verify` runs the backend tests, the frontend unit tests, a web build and
the Playwright journeys, in that order. The journeys depend on the build
because `vite preview` serves `dist` and does not build it: without that
prerequisite they pass against whatever was last built, which on 2026-10-04 was
a bundle seven hours older than the source and containing none of the interface
work it was reporting as sound.

The backend tests are every backend test, integration included, so `make
verify` needs Docker: the database fixture starts a PostgreSQL container and
migrates it. It was the not integration subset until 2026-09-06, which left 211
tests outside the gate, and both ISS-175 and ISS-177 lived in exactly that gap.
`make test-unit` is the offline subset for a fast loop, and neither slice
reports coverage, because a fraction of the suite measured against the whole
suite's threshold is a number that cannot be read.

A change that touches documents alone, Markdown, text, and anything under `docs/` or
`tasks/`, may be gated by `make verify-docs BASE=<the branch it merges into>` instead. It
runs the writing rules, the generated documents and the memory gate, which is everything a
document can fail, and it first refuses any change holding another file, naming it, because
the shortcut is only safe while no code changed. Approved by the owner on 2026-10-07,
CHG-0123: a thirteen line change to `project_map.md` had cost about fifteen minutes of tests.

## Architectural constraints

These are not style preferences. Breaking them costs a rewrite.

1. **`finops_core` never imports boto3.** No cloud SDK, no framework, no
   HTTP client. Domain and ports only. This is what makes GCP and Azure a
   connector instead of a rewrite.
2. **The canonical cost schema is FOCUS 1.1.** Do not invent a cost schema.
   Normalize at ingest.
3. **Scope is enforced in two places**, a request dependency and a repository
   guard. A route that forgets the dependency must still not be able to read
   out of scope data.
4. **Every fact carries `as_of`.** Every screen shows freshness.
5. **Partial failure is first class.** One account failing never fails a run.
   Error causes are typed: AccessDenied, Throttled, NotOptedIn, NoData. Never
   collapse them, and never render a failure as the number zero.
6. **Read only in v1.** No write API call into a member account. Remediation
   is delivered as a generated infrastructure as code pull request.
7. **The platform meters itself.** Every platform resource is tagged
   `finops:module`, and the platform's own cost is on the front page.
8. **The HTTP API is the single enforcement point.** The MCP server is a facade
   in front of it and calls it over the network with the caller's token. It
   never reaches into the service layer, because two implementations of an
   authorization rule is how an authorization bug is created. See ADR-0009.
9. **Cadence is data, not code.** Collection intervals live in
   `collector_schedule` with their reason and their cost. See ADR-0012.
10. **Two timestamps on every figure.** `as_of` is when the data was true at the
    source, `collected_at` is when Meter fetched it. Conflating them makes a
    stale number look fresh.
11. **Invariants are database constraints, not conventions.** If application
    code is the only thing preventing a bad row, the bad row will eventually
    exist. See `docs/07-DATA-MODEL.md`.
12. **Migrations are backward compatible, always.** Old and new task
    definitions run against the same schema during a rolling deploy. Add,
    backfill, then drop in a later release. Never rename or drop in the release
    that stops using the thing.
13. **Images are built for `linux/amd64`.** A push never converts an arm64
    image, and the failure reads as `exec format error`. `make build` pins it
    and `make verify-platform` checks it, by the label and by every compiled
    file inside, because a label once said amd64 over arm64 code. ISS-254.

## Commit format

```
<type>: <description>

<body explaining why, not what>
```

Types: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`.

One logical change per commit. No em dashes in the message. No attribution
trailer.
